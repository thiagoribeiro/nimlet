01 / THE IDEALESS TO BUILD. LESS TO OPERATE.

Your feature is messaging.
Your product is something else.

Chats, commands, notifications, agent conversations: different experiences, familiar infrastructure problems.

Nimlet gives you the essential communication layer. Your application owns the interface, the workflows and what events mean.

Read the design rationale ↗
01

Who can talk to whom?

Authenticated identities, memberships and room-level permissions.

02

What if the connection drops?

Persisted events and a sync cursor to catch up after reconnecting.

03

What happens on retry?

Idempotent event sends, so a repeated request doesn't add duplicates.

04

How do other systems join in?

HTTP APIs and AppServices for bots, integrations and external agents.

05 / INTERACTIVE EXPLAINERRECOVERY, NOT JUST DELIVERY.

A connection can disappear.
The conversation shouldn't.

Persist an event, disconnect a client, then reconnect. Nimlet's HTTP sync model lets the client catch up from a cursor instead of depending on a permanently open connection.

GET STARTED / BUILD SOMETHINGYOUR APPLICATION. YOUR INFRASTRUCTURE.

Less plumbing.
More building.

Run Nimlet alongside PostgreSQL and Redis, register a user, create a room, and send your first event. Start with the documented quick start; work directly with HTTP.

Full quick start ↗Browse the API ↗
# After registering and creating a room
curl -X PUT \
  "http://localhost:8080/rooms/$ROOM/send/m.room.message/txn1" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"msgtype":"m.text","body":"hello"}'
# Catch up on new events using HTTP long polling
curl "http://localhost:8080/sync?timeout=30000" \
  -H "Authorization: Bearer $TOKEN"

# Next request: pass the returned next_batch
# cursor as the `since` query parameter.
